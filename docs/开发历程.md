# 开发历程

从 v1.0 到 v2.2，一共 12 个可运行版本。这份文档按时间顺序记录每个版本遇到的具体问题、根因和修法。

不是功能清单，是踩坑记录。

---

## v1.0 · 起点：为什么不用 yt-dlp

最初的方案是标准的：用 yt-dlp 解析 B 站页面，拿到直链再下载。

第一次跑就撞墙——**HTTP 412 Precondition Failed**，一条视频都拿不到。

排查后发现不是代码问题：请求来自云主机机房 IP，B 站的风控直接拒绝。同一个链接在本地家宽上正常。这条路走不通，于是决定自己写客户端。

第一版架构定下来：

- 后端 `ThreadingHTTPServer`（只用标准库，能塞进嵌入式 Python）
- 前端原生 HTML/CSS/JS（零构建，改一行刷新就生效）
- 自研 B 站客户端：wbi 签名、`buvid3` 指纹 Cookie、DASH 取流、ffmpeg 合并
- 分片多线程下载

放弃 yt-dlp 这个决定后来证明是对的：自研客户端可以精确控制重试策略、画质降级、UA 切换，也比套一层外壳更容易调试。

## v1.1 · 两个致命 bug

**UA 永久降级。** 遇到 412 时，程序会把 `self.ua` 改成 curl 的 UA 绕过去。问题是改完**没有改回来**——整个进程从此都用 curl UA 请求 B 站，所有后续取流全部失败。

修法：改成临时降级（`try` 里改、`finally` 里恢复），并且只在当前这次请求生效。

> 教训：任何"临时改全局状态"的写法，都要配一个 `finally`。

**「3 小时 47 分只下第一个」。** 用户贴了一个合集链接，解析出来 100 多个条目，结果只下了第一个。

根因：解析器只处理了 `pages`（分 P），没处理 `ugc_season`（UP 主合集）和 `seasons_archives_list`（合集/系列）。所以返回的条目列表里只有第一条。

修法：新增 `_expand_media`，把三种结构（多分 P / UP 主合集 / 系列）都展开成统一的条目列表。

## v1.2 · 文件夹归属与选项语义

**目录平铺在一起。** 一次下多个合集，全都落在同一个目录，文件名还撞车。

修法：`Job` 的白名单字段里补上 `group` / `group_total`，`_download_one` 按 group 建子目录。

**选项区语义混乱。** 原来的选项是「视频 / 音频 / 全部」这种混着写的模式，用户根本分不清勾了会发生什么。

重新拆成两组：

- **输出**：视频 / 仅音频（互斥）
- **附加**：封面 / 字幕 / 弹幕（可多选）

这个结构一直沿用到现在。

## v1.3 · 1080P 下出来是糊的

用户选了 1080P，下出来画面很糊。

根因不是下载坏了，是**没有登录**。B 站未登录只给到 480P，而程序的画质降级逻辑写错了：`qn_for_height` 的映射表把 1080 算成了 64（720P）以下。

修法：

```python
>=2160 → 120   # 4K
>=1080 → 80    # 1080P
>=720  → 64    # 720P
>=480  → 32    # 480P
else   → 16    # 360P
```

同时**预估体积**也改了：未登录按 720P 封顶计算，不再拿 1080P 的码率估，避免"预估 2GB 实际 800MB"。

## v1.4 · 扫码登录与分组折叠

**登录。** 手填 Cookie 的意愿太低，改成扫码：调 `passport-login/web/qrcode/generate` 拿二维码，轮询 `poll` 拿状态（86101 未扫 / 86090 待确认 / 0 成功 / 86038 过期）。成功后从响应里提取 `SESSDATA` / `bili_jct` / `DedeUserID` 存下来。

**分组折叠。** 一个 100P 的列表全展开有几百行，根本没法看。改成按 group 分组，第一组展开、其余折叠成组头。

---

## v1.5 · 进度条不动、失败就整条废掉

**进度条一格一格卡住。** 因为总长度靠 `Content-Length` 估，而 B 站 CDN 的 HEAD 响应经常给一个偏小的值，导致进度条早早冲到 100% 又回退。

修法：用 Range 请求 `bytes=0-1`，从 `Content-Range: bytes 0-1/总长` 里读真实长度。这个值才可信。

**失败一次就整条废掉。** 网络抖一下就报错，不会自己重试。

加了自动重试：失败后重试 3 次，每次换线程数（8 → 4 → 2），并强制走 Range 请求。

**进度更新太频繁。** 每个分片回调都重建 DOM，卡顿。改成 `card._built` 只建一次 DOM，后续只改文字和宽度。

---

## v1.6 · 单条取消与加权进度

**想取消其中一条，只能取消整个任务。**

加了 `cancel_item` 接口和条目级的 `.mini-btn`。每个条目自己带一个 `CancelToken`，取消时只置自己那个。

**进度条跳得太快。** 20 条视频按"条数"算进度，下完第 1 条（3 分钟）就 5%，下完第 20 条（40 分钟）也才 100%，比例完全失真。

改成**按时长加权**：每条按 duration 占比分配权重。

**分片校验失败。** 单片下坏了直接整条重来。改成单片的 3 次重试。

**权限类错误不该重试。** 「该视频需要大会员」「已下架」这种重试一百次也没用。加了 `_retryable_error` 把这类排除掉。

## v1.7 · 三个用户报的 bug

**① 取消的条目被判成"有失败"。** 用户取消了一条，任务结束却显示"有失败"。

根因：收尾统计只看 `err_n`，没区分 cancelled。改成统计 `cancelled_n` 和 `err_n` 两个数，`err_n == 0` 且全部 done/cancelled 时判 `done`，日志写"完成 N 个，取消 M 个"。

**② 目录名没有归属。** 下载出来一个叫「英语」的文件夹，完全不知道是谁的。

改成从接口返回里取 UP 主名字拼接：收藏夹用 `info["upper"]["name"]` 拼成 `XX的「英语」收藏夹`，UP 主投稿用 `vlist[0]["author"]` 拼成 `XX 的投稿`。

实测输出：`BlockChain频道的「英语」收藏夹`。

**③ 预估偏大 + 选 1080 却下 480。** 两个问题叠在一起：预估按 1080 算（实际只能拿 480），所以数字虚高；扫码登录因为 nav 校验被风控（-412）误判成失败，用户以为登录了其实没登。

修法：预估改成"未登录按 720 封顶"；登录判定改成"只要拿到 SESSDATA 就算成功"，不再依赖 nav 接口。

## v1.8 · 三个产品功能

**三档文件整理方式。**

- `flat` 平铺（默认，保持原有习惯）
- `per_item` 每条一个文件夹
- `by_type` 按类型分目录，目录名加了数字前缀 `1 视频` `2 字幕` `3 弹幕` `4 封面`，让视频排最前面

三档都在真实下载里验证过目录树。

**选择本地下载目录。** 用纯 ctypes 调 `shell32.SHBrowseForFolderW`，零依赖。

这里有个必须显式设置的点：`restype` / `argtypes` 不设，64 位下指针会被截断成 32 位，直接崩。

**包体没变。** 用户明确说过"如果要变得很重型的话那就算了"。加完这些功能包体仍是 47.7MB，零增长。

## v1.9 · 全面代码审查

用户要求"细致检查 bug"。通读 3807 行，修了 6 个真实 bug、2 个优化。

**① 取消过的条目点重试永远复活不了**（最严重）

`_api_retry` 只重置了 `job.cancel_token`，没重置每个 item 自己的 `_token`。那条带着"已取消"标记被秒判取消。

实测：修前取消 1 条、重试后状态还是 cancelled；修后 4/4 全部 done。

**② 单流下载失败被当成成功**

`_download_single` 失败 `return False`，上层不检查返回值，继续调 ffmpeg 合并一个不存在的文件，最后报"ffmpeg 合并失败"，把真实原因完全掩盖。

改成失败直接 `raise IOError("下载失败：%s" % e)`，重试机制能接住。

**③ 重试后总进度翻倍**

`rewind()` 清零 done 但保留 total，第二次又 `add_total`，总量翻倍，百分比最多 50%。修法：`rewind` 里把 `self.total = 0`、`_frozen = False`。

**④ 分片线程数失控**

"一片一线程"，100MB 按 6MB 切片 = 17 个线程同时打 CDN。这是"分片校验失败"的诱因之一。

改成 `queue.Queue` + 固定线程池，线程数 `min(threads, len(segments))`。实测峰值 8 个下载线程（进程总线程 11）。

**⑤ 超长标题写盘失败**

`make_safe_filename` 按字符截断，中文 3 字节/字，84 字 = 252 字节逼近 255 上限，报 `File name too long`。

改成字节级循环压到 ≤200 字节，且 `_download_one` 里 `max_title` 按目录深度动态算、上限 60。

实测 240 字标题正常完成。

**⑥ 字幕时间戳可能非法**

`int(round((sec - int(sec)) * 1000))` 可能得到 1000，生成 `00:00:01,1000`，有些播放器整个字幕错位。

改成整数毫秒 `total = int(round(sec * 1000))` 后再取模。

**两个优化：**

- **已存在跳过**：`_download_one` 提前算 `out_path`，存在且非空就跳过。实测重复下载 3.0s → 0.9s。
- **未登录画质封顶**：`if not cookie: target_qn = min(target_qn, 64)`，省掉 3~4 次注定失败的 playurl 请求。

## v2.0 · 产品化三件事

这一版不是修 bug，是补产品能力。核心是同一套"记住每条下到哪了"的基础设施。

**断点续传**

原来的问题：临时路径用任务内序号（`seq`）命名，`seq` 每次任务都不同，重开后找不到旧分片；`_run_once` 从 0 开始；`_run_job` 结尾 `shutil.rmtree` 把临时目录全清掉。中断必然全丢。

改造：

- 新增 `records.py`，提供 `Records`（下载记录）和 `Cache`（续传缓存）
- 缓存目录用 `md5(bvid|cid)` 命名，稳定不随任务变化
- 分片写盘的同时写 `parts-video.json`，记录 `{size, chunk, done: [...]}`
- `_run_once` 读取 manifest，跳过已完成的片；片大小对不上就丢弃重下
- 整段下载（<8MB 或单线程）也支持：保留 `.tmp`，重开时用 Range 从断点续
- 合并成功后清缓存；缓存超 7 天没动或总量超 4GB 自动清理

实测：13MB 视频（7 片）下到 6 片时 `kill -9`，重启后任务显示"已中断"，点继续 **4.82 秒**补完。

**任务持久化**

`JobManager.jobs` 是内存字典，`Job` 没有序列化方法，重启就清空。

改造：`Job.to_dict()` / `Job.from_dict()`，1.5 秒节流写 `data/tasks.json`；启动时加载，状态为 `running` / `queued` 的改成 `interrupted`，前端显示"已中断"+"继续下载"。

**增量下载**

`_api_parse` 返回时给每个条目附 `downloaded` 标记，前端显示绿色角标，默认只勾未下载的，另加"只选新增"按钮。

实测 253 条收藏夹：1 条已下载，界面显示"已选 252 / 253"，那条带角标且未勾选。

**这一版自己引入又修掉的三个问题：**

1. `Cache.drop` 对非空目录静默失败，缓存删不掉 → 改 `shutil.rmtree`，并加路径保护（只允许删缓存根目录下的）
2. 每次进 `_download_one` 都建缓存目录，导致"已存在跳过"也留一个空壳目录 → 改成只在真正要下载时建
3. 任务跑完没触发保存，`tasks.json` 里还留在"下载中"，重启被误判成"已中断" → 完成、取消、重试三处都补了保存触发

## v2.1 · 番剧时长单位

用户报番剧解析后预估严重偏高。查下来是 `/pgc/view/web/season` 返回的每集 `duration` 单位是毫秒，代码当秒直接喂给了预估公式。

三个连锁后果：列表里每条时长显示成 300~400 小时（一集 25 分钟的番剧）；预估体积虚高 1000 倍（一集 58.2GB，实际 191MB）；进度加权被单集吃满。`app.py` 里的 `durs` 权重读的是同一个字段，所以进度条同样被放大。

修法是新增 `_pgc_seconds()`，超过 86400 的值按毫秒折算，其余按秒返回——一集番剧不可能超过 24 小时，这条线足够安全，同时兼容个别返回秒的情况。顺手把番剧条目名从裸集号改成「集号 + 长标题」，146 话的列表终于能认出是哪一集。

对比普通视频：`/x/web-interface/view` 的 `pages[].duration` 是秒，UP 主合集的 `seasons_archives_list` 也是秒，只有 pgc 这一套是毫秒。同一个平台的不同接口各用各的单位，没有统一约定可依赖。

实测宝可梦 ss23795（146 话）单集 24分28秒，全选 60小时10分；凡人修仙传 ss28747（317 话）单集 17.9~20.1 分钟。

## v2.2 · 同一个视频换画质重下

用户报：先用 720P 下过一条视频，之后改选 4K 再下，第二次几秒就「完成」，盘里还是那份低画质文件。

根因在 `_download_one` 的跳过判断：`out_path` 由 `stem` 决定，而 `stem` 只由标题拼出来，路径里没有任何画质信息。于是「文件在」被当成「已下载」，不管这份文件是什么画质。

同一条根因往下还有三处连锁：

1. `records.py` 的 `mark()` 只存 `{title, file, size, ts}`，不存画质——即使想比对也没有依据
2. `_api_parse` 只回传布尔 `downloaded`，前端默认只勾未下载条目，于是 720P 下过的条目在 4K 模式下一条都勾不上
3. 缓存目录 `cache.dir_for(bvid, cid, ep_id)` 不带画质，720P 的残缺分片会被 4K 复用，分片大小对不上会下坏

修法分四层，都围绕一个概念：把「实际拿到的画质」变成一个可比较的标签。

① 新增 `quality_tag(info, max_h, opts, audio_only)`，返回 `(缓存标签, 人读名)`。视频取 `pick_video()` 之后的实际 `height` + codec 拼成 `v720_AVC1`，仅音频取 `a<pref>`，durl 老格式取 `durl`。

② `records.mark()` 增加 `qual` / `qual_text` / `max_h` 三个字段。

③ `tmp_dir = cache.dir_for(bvid, cid, ep_id, tag=qtag)`，缓存按画质分目录。

④ 跳过判断改成比对记录里的 `qual`：不同就记日志「已有 X，本次要 Y，重下并覆盖」并继续走下载流程（覆盖同名文件），相同才跳过。老记录没有 `qual` 字段时 `prev_q` 为空，走原来的跳过分支——向后兼容，不打扰已经下过的人。

**验证时踩了个自己的坑。** 第一次拿 `BV1GJ411x7h7` 做用例，先 480P 再 720P，第二次仍然「已存在，跳过」，看起来像没修好。其实这个视频未登录封顶就是 480P，两次 `quality_tag` 都算出 `v480_AVC1`，产物确实相同，跳过是对的。换成 360 → 720 → 720 三次串行才验证到位：前两次各自日志「重下并覆盖」，文件在 26,347,806 和 14,767,126 字节之间来回变，第三次才跳过。

> 这条经验值得记下来：判据必须是「实际能拿到的画质」，不是「用户请求的档位」。B站按登录状态、会员状态、视频本身的上限三重截断，请求 4K 拿到 480P 是常态。

**前端也得跟着改。** 只给布尔 `downloaded` 不够——720P 下过的条目在 4K 模式下到底算不算已下载，取决于当前选的画质。新增 `dlFlags(it)`：未下载返回 `no`；`dl_max_h` 为 0（老记录）或等于当前画质返回 `yes`，显示「已下载」并置灰；不同返回 `stale`，显示「已下 480P」（琥珀色，不置灰）。默认勾选、`nOld` 统计、「只选新增」按钮、`#optQuality` 的 change 监听全部改用 `dlFlags(...).state !== 'yes'`；切画质时按新画质重算一遍勾选，有 stale 就 toast 提示。

**顺带修的老问题。** 顶栏版本徽标在 `index.html` 里写死 `2.0`，`/api/status` 早就返回正确版本但没人用。改成 `id="brandVer"`，`loadStatus()` 里从接口回填——版本号只留 `APP_VER` 一个真相源。

**实测。** 360P 产物 14.7MB、480P 产物 26.3MB，切换后文件字节数确实变了；`records.json` 里留下 `qual=v480_AVC1` / `qual_text=480P 清晰 · AVC1` / `max_h=720`。前端三段验证：1080 时角标「已下 480P」且勾选，切 720 变「已下载」且不勾，切 360 又变回勾选并弹提示。

## 贯穿全程的几个判断

**只用标准库。** 后端零第三方依赖，这直接决定了分发包能做到 47.7MB（含 ffmpeg）。

**前端零构建。** 原生 JS 写 997 行，改一行刷新就生效，没有构建等待。

**遇到 B 站接口变动就加兜底而不是硬改。** 比如 space 接口有新旧两套，`_parse_space` 主接口失败会落到旧接口。

**不做"顺便优化"。** 每一版只改用户当次报的问题和它们的直接根因，避免引入新的不确定性。v2.0 之前所有功能都在真机跑过一遍，不是纸面通过。
