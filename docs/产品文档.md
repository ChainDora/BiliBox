# 产品文档

> 单人自用的工具型产品。这份文档记录它要解决什么问题、怎么设计的、为什么这样取舍。

---

## 一、背景

### 问题从哪来

B 站是个学习资料库。考研英语、数学、408、政治，大量的免费课程都在上面。但 B 站官方只提供"缓存"——缓存在 App 里，只能在 App 里看，不能导出，换设备就没了，离线也受限。

而真实的使用场景是：**在电脑上下载，装到平板或手机上看。**

原因很实际：平板续航长、屏幕大、可以躺着看，比抱着笔记本看舒服得多。但 B 站没有"下载到本地再传到平板"的功能。

### 已有的方案为什么不够用

| 方案 | 问题 |
| --- | --- |
| 录屏 | 画质损失严重，一个 40 分钟的视频要录 40 分钟 |
| 浏览器插件 | 大量插件已失效；能用的只支持单条；批量下六七十条基本会挂 |
| yt-dlp 命令行 | 需要装 Python 环境、要敲命令；普通用户门槛太高 |
| 各种"在线解析"网站 | 上传链接给别人，隐私和稳定性都没保障；大文件基本不支持 |

所以目标很明确：**一个不需要命令行、能批量、能自己控制的东西。**

### 为什么是"本地网页界面"

最初考虑过三种形态：

1. **命令行工具** — 开发最快，但用户明确说了不要。"我不想敲命令"
2. **桌面 GUI（PyQt / tkinter）** — 嵌入包体积增加明显，界面也不好看
3. **本地网页界面** — 后端起 HTTP 服务，浏览器打开

选了第三种。理由：

- 界面用 HTML/CSS 写，好看且改起来快，不用学 Qt 那套
- 浏览器是现成的渲染引擎，不吃包体
- 免安装：解压双击，浏览器自动打开，不用装任何东西
- 后续如果要做"局域网访问"（平板直接点播），这条路天然支持

代价是需要一个本地端口。端口被占会自动顺延（8931 → 8932 → 8933）。

## 二、目标用户与场景

### 用户画像

一个考研备考生，有一台 Windows 笔记本、一台平板。日常在 B 站上跟几个固定 UP 主的课，习惯把课攒进收藏夹，一次下一批。

技术水平：会用电脑，但不愿意折腾命令行和开发环境。

### 三个核心场景

**场景 A：一次下一整个收藏夹**

收藏夹里攒了 253 条英语课，总共约 36GB。希望一次勾选、一次下完，下完之后在平板上一集一集看。

关键诉求：**能下完**。这不是"下一条试试"，是几小时的连续任务，中途一定会遇到网络波动、电脑休眠、需要关机。

**场景 B：收藏夹每周更新**

UP 主每周更新两三集。已经下过 250 条，只想下新增的 3 条。

关键诉求：**别让我重新勾 253 个**。

**场景 C：单条补下**

某一条下失败了，或者当时没勾，后来想补。

关键诉求：**能单独重试，不要整个任务重来**。

## 三、功能设计

### 3.1 输入

支持六种链接，一个输入框自动识别：

| 类型 | 示例 | 解析结果 |
| --- | --- | --- |
| 单视频 | `BV1xx...` | 1 条 |
| 多分 P | 同一 BV 下多个 P | N 条，带 P 序号 |
| UP 主投稿 | `space.bilibili.com/xxx` | 该 UP 的全部投稿 |
| 合集 / 系列 | `series` / `season` | 合集内全部视频 |
| 收藏夹 | `list/mlxxxx` | 全部收藏条目 |
| 番剧 | `ss` / `ep` | 整季或单集 |

解析完展示：封面、标题、UP 主、条目数、每条时长、总预估体积与总时长。

**为什么要有预估体积。** 36GB 不是小数目，下之前得知道要占多少硬盘。这个数字按"未登录 720P 封顶"算，因为未登录只可能拿到这个画质，报 1080P 的码率会虚高。

### 3.2 选择

- 全选 / 反选 / 按范围选
- 标题搜索过滤
- 分组折叠：合集默认只展开第一组，其余折叠成组头（100P 全展开有几百行，没法看）
- **已下载标记**：下过的条目带绿色角标，默认不勾选，"只选新增"按钮一键只勾没下过的

### 3.3 下载选项

拆成两组，避免语义混乱：

**输出（互斥）**
- 视频（mp4，音视频合并）
- 仅音频（m4a）

**附加（多选）**
- 封面（jpg）
- 字幕（srt）
- 弹幕（转 ass，可在播放器里作为字幕加载）

另有两项全局设置：画质（最高 8K，实际受登录态限制）、编码（AVC / HEVC / AV1）、音质。

### 3.4 文件整理

三档，用户可选，默认保持平铺：

| 模式 | 效果 | 适合 |
| --- | --- | --- |
| `flat` 平铺（默认） | 所有文件在同一目录，按序号命名 | 习惯用文件夹管理器自己整理 |
| `per_item` | 每条视频一个文件夹 | 单集带封面/字幕/弹幕时不至于一堆散文件 |
| `by_type` | `1 视频/` `2 字幕/` `3 弹幕/` `4 封面/` | 想把同类文件放一起 |

三档都做了真实下载验证。目录名加数字前缀是为了让视频目录排在最前面——不这样的话按字母序"封面"会排在"视频"前面。

**为什么默认是平铺。** 用户第一版就用平铺，明确说过"默认保持当前这种就好"。产品改动不应该动用户已经形成的习惯。

### 3.5 下载中

任务卡展示：标题、总进度（按时长加权）、当前第几条、画质、瞬时速度、剩余时间、已下/总量。

明细可展开，每条显示序号、标题、状态、大小、单条取消按钮。

**进度为什么按时长加权。** 按条数算的问题很明显：20 条视频里第 1 条 3 分钟、第 20 条 40 分钟，按条数算下完第 1 条就 5%，完全失真。按 duration 分配权重，进度才符合直觉。

### 3.6 失败与重试

- 单条取消：只置该条目自己的取消标记
- 单条/整体重试：重置所有取消标记（包括每个条目的 `_token`），否则会被旧标记秒判取消
- 分层重试：8 线程 → 4 → 2，并强制走 Range 请求
- 权限类错误（需要大会员、已下架）不重试，因为重试一百次也没用

### 3.7 已下载面板

按目录聚合展示已下内容，点"打开文件夹"直达资源管理器。这样下完一批不用自己去翻路径。

## 四、三个关键设计决策

### 决策一：不用 yt-dlp

**背景**：初测 yt-dlp 直接 412，诊断出是机房 IP 风控。

**判断**：即使换网络环境能跑，yt-dlp 也无法精细控制 B 站特有的逻辑——wbi 签名参数、画质降级顺序、字幕接口、弹幕 XML 转 ASS。套一层外壳反而更难调试。

**结果**：自研客户端 1032 行，覆盖了全部需要的接口，且每个失败点都能精确控制重试策略。

### 决策二：分片用固定线程池

**背景**：早期"一片一线程"，100MB 按 6MB 切片 = 17 个线程同时请求 CDN。这是"分片校验失败"的主要诱因。

**判断**：并发不是越多越好。CDN 对单 IP 的并发连接有限制，超了就开始截断响应。

**结果**：`queue.Queue` + 固定线程池，线程数 `min(用户设置, 片数)`。实测峰值 8 个下载线程。

### 决策三：断点续传的粒度选"分片级"

**三个可选方案**：

1. 文件级（记录"这条下完了没"）— 太粗，一条 175MB 的视频中断等于重下
2. 分片级（记录"哪些片完成了"）— 中等
3. 字节级（记录"下到第几个字节"）— 太细，需要服务端支持精确 Range，且 manifest 写盘频率高

选了分片级。分片大小 2~6MB，最坏情况重下 6MB，可接受；manifest 每片完成写一次，写盘频率也可控。

实现上的关键点：**缓存目录必须稳定**。原来用任务内序号（`seq`）命名，重开后 `seq` 变了就找不到旧分片。改成 `md5(bvid|cid)`。

## 五、明确不做的事

| 不做 | 原因 |
| --- | --- |
| 命令行版本 | 用户明确拒绝 |
| 手填 Cookie | 意愿低，扫码更好 |
| 读浏览器 Cookie | `SESSDATA` 是 HttpOnly，技术上读不到 |
| 破解析付费内容 | 只下用户有权访问的内容 |
| 自动上传/转发 | 定位是本地备份工具 |
| 内嵌播放器 | 浏览器/系统播放器已经够用，做播放器是另一个工程 |
| 服务端部署 | 机房 IP 容易被风控，本地跑才稳 |

## 六、后续规划

### P1（体验提升明显）

**局域网点播** — 下完之后，平板浏览器打开电脑的地址就能直接播，不用拷文件。这是"下完要在平板看"这个场景的自然延伸。

**失败原因分组** — 现在 20 条失败都长一个样。应该分成"重试有用"（网络超时）和"重试无用"（需要登录、已下架）。

**磁盘空间预警** — 预估 36GB 但盘里只剩 10GB 时，应该在下之前拦住，而不是下到一半报"空间不足"。

### P2（锦上添花）

- 任务总览：今天下了多少、队列还剩多少
- 登录有效期提示：别下到一半掉线
- 首次使用三步引导
- 完成后系统通知
- 限速（一边看网课一边下载不抢带宽）

功能是否真的可用，靠实测而不是纸面通过。下面这些都是真实跑过的：

| 项目 | 结果 |
| --- | --- |
| 253 条收藏夹解析 | 0.54s |
| 100 条任务创建 | 0.00s |
| 并发 3 个任务 | 6.4s 全部完成 |
| 25MB 单文件 | 4.1s，6.1 MB/s |
| 100 分 P 合集 | 目录结构正确，编号连续 |
| 取消 1 条 + 重试 | 3/4 → 4/4 |
| 13MB 视频下到 6/7 片强杀 | 重启后 4.82s 补完 |
| 240 字超长标题 | 正常完成（修前报 File name too long） |
| 非法链接 4 种 | 全部 400 拒绝 |
| 不可写目录 | 正确拒绝并提示 |
| 重复下载同一批 | 3.0s → 0.9s（已存在跳过） |

**未验证**：Windows 实机全流程（没有 Wine 环境），只做到 zip 结构校验和文件完整性检查。
